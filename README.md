# Graphing Labrador

A Year 9 Mathematics graphing platform set in **Vector Lab**, with five Labrador guides (Hector, Tex, Axel, Slobber, Kirby), interactive graphs, explicit teaching, evidence-based diagnostics and a cosmetic reward system.

React 19 + TypeScript + Vite + Tailwind CSS 4 + React Router + Recharts + Lucide. Tests: Vitest and React Testing Library.

## Run it

Requires Node.js 20+ (this project was built with Node 24 LTS).

```bash
npm install
npm run dev        # http://127.0.0.1:5173/
```

| Script | Purpose |

## Demo mode

Open the site and choose **Enter as Demo Student** (Sam) or **Enter as Demo Teacher** (Mr John Leary). The sidebar has a clearly labelled "Switch to demo teacher/student" button.

- All people are fictional. Ten students are seeded with realistic attempts generated by running the real scoring code on the real question bank.
- Progress, purchases and marks are saved in **this browser's localStorage only**. They are not synchronised between users or devices. Use **Reset demo data** on the landing page to start over.
- Demo logic lives in `src/services/persistence` and `src/data/demo`. Pages never branch on "is this demo?"; they call the actions in `src/services/persistence/actions.ts`. A production adapter replaces that module.

## Try the vertical slice

1. As the student: **Start lesson** on the dashboard. Play *Understanding Gradient*: drag point B, follow the I do think-aloud, answer We do / You do, spot Maya's mistake, interpret a cyclist's speed with units, do the checkpoint (including plotting by click or by typing coordinates), and write a reflection.
2. Try wrong answers: reversing rise/run (`2` instead of `1/2`), dropping a negative sign, and omitting `km/h`. Each gets specific feedback and is tagged.
3. Spend coins in **Reward Shop**, then equip items in **My Kennel**. The same look appears in the sidebar and dashboard.
4. Switch to the teacher: the dashboard, student profiles (attempt history, skill evidence, misconception evidence, interventions, notes), **Results & Marking** (rubric marking of the reflection), **Lesson Library** (teacher view) and **Rewards Settings**.

## Maths and scoring

- Graph maths is pure and tested: `toPixel`/`toMath`, `gradient` (a vertical line is **undefined**, a horizontal line is 0), intercepts, line clipping, snapping.
- Answers accept `0.5`, `1/2`, `2/4`, `.5` and a Unicode minus; decimals use a tolerance. Units are required for rate questions (number credited, unit marked).
- Open responses are never auto-marked; they go to the teacher with a rubric.
- Wrong answers get error-specific feedback and a tag (`rise-run-reversed`, `negative-sign-ignored`, `xy-reversal`, ...). Generic errors never reveal the answer.

## Rewards

XP (permanent) and coins (spendable) are an append-only ledger. Per question and student: **correct first try 10 coins + 5 XP; first attempt wrong 3 coins + 1 XP; later wrong attempts 0; first correct after a wrong attempt 5 coins + 2 XP; anything after completion 0.** Reward keys plus the saved attempt history make this idempotent across refreshes and rapid clicks. Invalid input earns nothing, and a written reflection is never treated as correct (it earns the first-attempt amount once). Daily check-in (5 coins) and the lesson bonus (40 coins, 50 XP) are separate and teacher-editable; the per-question amounts are fixed.

## Feedback and answer checking

Auto-marked questions show exactly `Correct! Well Done!` or `Incorrect! That's ok, give it another go!` (`src/lib/scoring/messages.ts`). The correct answer is never shown after a wrong attempt; an optional hint can be requested. Numeric answers are parsed into a number and a unit separately (`src/lib/scoring/parse.ts`), so `15km/h`, `15 km/hr`, `15 kilometres per hour` and `30/2 km/h` are accepted while `15 m/s`, `-15 km/h` and `15` (no unit) are not.

## Maths notation

KaTeX renders fractions, exponents, subscripts and units. Authors write `$...$` (inline) or `$$...$$` (display) in question data. Rise, run and negative values are emphasised with `\htmlClass` (`m-rise`, `m-run`, `m-neg`), and every rendered expression has an `aria-label` text alternative.

## Diagnostics

Evidence is split into *independent* (You do / application / checkpoint, no hints) and *supported* (We do, hints). Completion and time are not used as mastery evidence. Mastery with fewer than 3 independent items is labelled provisional. A misconception is "possible" after one tagged error and "likely" only when the same error appears on two or more different questions. Every conclusion links to the underlying attempts.

## Curriculum

Mappings are stored as **draft** and never show official outcome codes. A teacher must validate them against the NSW Mathematics K-10 (2022) syllabus (https://curriculum.nsw.edu.au/learning-areas/mathematics/mathematics-k-10-2022/overview/course) before official codes are added.

## Connecting a production database (Supabase)

1. Create a Supabase project. Run `supabase/migrations/0001_initial_schema.sql`, then optionally `supabase/seed.sql`.
2. Copy `.env.example` to `.env` and set `VITE_APP_MODE=production`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`. Only the anon key goes in the frontend; never a service-role key.
3. Implement a production adapter with the same function names as `src/services/persistence/actions.ts`, backed by Supabase Auth and the tables. The schema already includes Row Level Security (students read only their own evidence; teachers read only their enrolled students; answer keys are teacher-only), an idempotent `award_reward`, and a locked `purchase_item` function. Scoring (`submit_attempt`) still has to be written as an Edge Function; it is marked TODO in the migration.

Browser storage must not be used for multi-user production data. **This repository is not production-approved.**

## Deployment

`npm run build` produces static files in `dist/`. For GitHub Pages set `VITE_BASE=/<repo>/` when building. Routing uses the URL hash, so no rewrite rules are needed.
